# RFC: 토큰을 한 원본에서 생성한다

> 상태: **초안** | 검토 중 | 확정 | 기각 | 대체됨(→ RFC #N)
> 작성일: 2026-09-14 · 등급: L3 · 승인: 미승인
>
> **이 RFC 는 지금 착수하자는 제안이 아니다.** 착수 조건(§8)이 충족되기 전까지는 기록으로만 둔다.

---

## 1. 문제

semantic 토큰이 **네 곳**에 같은 내용으로 존재한다.

| 위치 | 형태 | 누가 읽는가 |
|---|---|---|
| Figma `Se/` 컬렉션 (Kiio-Library) | 디자인 변수 | 디자이너 · 사람 |
| `src/tokens/semantic.ts` | TS 객체 | 쇼케이스 Tokens 페이지 |
| `src/tokens/tokens.css` | CSS 커스텀 프로퍼티 | **모든 컴포넌트**(런타임 진실) |
| `tailwind.config.js` | `var()` 참조 트리 | Tailwind 클래스 생성 |

2026-09-13 실측에서 네 곳이 실제로 갈려 있었다. 불일치 **24건**:

- `tokens.css` 에만 있는 키 6개 × 2테마 = 12 — 컴포넌트가 필요해서 만들었고 Figma 에는 없었다
- `semantic.ts` 에만 있는 키 2개 — 세 스케일이 한 인터페이스를 공유해 Alpha 에 없는 `1000` 이 생겼다
- `tailwind.config.js` 에 빠진 키 3개 — CSS 에 있어도 클래스로 못 쓰니 소비자에게는 없는 것과 같다
- `semantic.ts` 의 dark `Divider.Alpha` 값 5개 — 주석이 "white-alpha 는 CSS 가 처리"라고 **인정하면서** 값은 검정 알파였다

**지금 이 문제는 검사로 막혀 있다.** `figmaContract.test.ts` 의 T8 이 4자 정합을 판정하고, 위 24건은 전부 해소됐다. 그러나 검사는 **어긋남을 알려줄 뿐 손으로 네 곳을 맞추는 일을 없애지 못한다.** 이 RFC 가 다루는 것은 그 수작업이다.

**트리거**: 토큰을 추가·변경할 때마다 네 파일을 편집해야 한다. 실제로 2026-09-14 작업 중 Tailwind 편집에서 `neutral-solid-800` 을 실수로 지웠고 T8 이 그것을 잡았다 — 검사가 있어 사고는 막혔지만, **그 실수가 가능하다는 사실 자체**가 이 RFC 의 근거다.

## 2. 선택지

| 선택지 | 내용 | 비용 | 되돌리는 비용 |
|---|---|---|---|
| **A. 스냅샷에서 생성** | `specs/tokens/semantic.figma.json` 을 원본으로 `semantic.ts`·`tokens.css` 의 semantic 블록·`tailwind.config.js` 의 색 트리를 스크립트로 만든다 | 생성기 1개(~200줄) + 빌드 단계 1개. 생성물이 커밋되므로 diff 가 커진다 | 생성물을 손으로 유지하는 상태로 되돌리면 된다 — 생성기를 지우는 것으로 끝 |
| B. Figma API 직접 호출 | 빌드가 Figma 를 직접 읽는다 | 토큰·네트워크·CI 비밀이 필요하다. Figma 가 죽으면 빌드가 죽는다 | A 보다 크다 |
| C. Style Dictionary 도입 | 표준 도구로 옮긴다 | 설정 학습 + 이 저장소의 3층 구조(primitive/semantic/comp)를 그 모델에 맞춰야 한다. `--comp-*` 는 컴포넌트별 규칙이 많아 그대로 옮겨지지 않는다 | 크다 |
| **D. 아무것도 하지 않음** | T8 이 어긋남을 잡는 상태를 유지한다 | 0. 토큰 변경마다 네 곳 편집이 남는다 | — |

**"아무것도 하지 않음"이 지금의 기준선이다.** 검사가 있으므로 어긋남은 배포되지 않는다. 비용은 편집 노동뿐이고, 토큰이 안정된 지금 그 빈도는 낮다.

## 3. 확정 방향

**미정.** 착수 조건(§8)이 오면 A 를 검토한다.

A 를 우선하는 이유(원칙 2 — 시스템으로 판단 대체): 생성기는 "네 곳을 맞춘다"는 규칙을 사람의 손에서 코드로 옮긴다. B·C 와 달리 외부 의존성이 늘지 않고, 스냅샷이라는 중간 파일이 이미 있어 절반은 만들어져 있다.

## 4. 설계 (A 를 고를 경우)

```
specs/tokens/semantic.figma.json   ← 사람이 갱신(Figma 에서 뽑아 적는다)
            │
            ▼  scripts/generate-tokens.mjs
   ┌────────┼────────────────┐
   ▼        ▼                ▼
semantic.ts  tokens.css      tailwind.config.js
(light/dark) (semantic 블록만) (semantic 색 트리만)
```

**생성하지 않는 것**이 중요하다.

- **dark 값**은 코드가 소유한다(2026-09-13 확정). 스냅샷에 없으므로 `tokens.css` 의 `[data-theme="dark"]` 는 **사람이 유지**한다. 생성기는 light 만 만들고 dark 는 건드리지 않는다.
- `--comp-*` 토큰, primitive 블록, 모션·크기 토큰은 대상이 아니다.
- `tailwind.config.js` 의 나머지(모션·타이포 플러그인·radius)도 그대로 둔다.

즉 생성 범위는 **각 파일의 semantic 색 부분**이고, 경계를 주석 마커(`/* GENERATED:semantic-start */`)로 표시한다.

## 5. 영향 범위 — 공개 표면 diff

| 대상 | 변경 | 파괴적인가 |
|---|---|---|
| `--semantic-*` 토큰 이름 | 없음 — 생성 결과가 현재와 같아야 착수할 수 있다 | 아니오 |
| `semantic.ts` export 타입 | 없음 | 아니오 |
| 개발 절차 | 토큰 변경 시 스냅샷을 고치고 `npm run tokens:generate` 를 돌린다 | 절차 변경 |

**착수의 전제**: 생성기를 처음 돌렸을 때 **현재 파일과 바이트 단위로 같아야 한다**. 다르면 그 차이가 곧 숨은 불일치이므로 먼저 그것을 해소한다.

## 6. 검증 방법

- [ ] 자동 — T8(`figmaContract.test.ts`)이 그대로 판정한다. 생성기가 틀리면 T8 이 red 를 낸다. **검사를 먼저 만들어 둔 것이 이 순서를 가능하게 했다.**
- [ ] 자동 — `npm run check` 에 "생성물이 최신인가"를 넣는다(생성 후 git diff 가 비어 있는지).
- [ ] 수동 — 쇼케이스 Tokens 페이지를 light/dark 로 보고 값이 그대로인지 확인.

## 7. 롤백

생성기를 지우고 생성물을 손으로 유지하는 상태로 되돌린다. 생성물이 커밋돼 있으므로 **파일을 되살릴 필요가 없다** — 스크립트만 빠진다.

## 8. 착수 조건

다음 중 **하나라도** 일어나면 이 RFC 를 검토 단계로 올린다.

1. **T8 이 두 번째로 red 를 낸다** — 손으로 맞추는 비용이 실측되는 시점이다. (첫 번째는 2026-09-13 의 24건이고 그때 해소했다.)
2. **semantic 패밀리가 추가된다** — 한 패밀리가 늘 때마다 네 곳에 10단씩 적어야 한다.
3. **다크 모드의 원본이 Figma 로 옮겨진다** — 생성 범위가 두 배가 되어 수작업 비용도 두 배가 된다.

## 부록 — 논의 기록

**왜 검사가 먼저였나.** 생성기를 먼저 만들었다면 "생성 결과가 옳은지"를 판정할 수단이 없었다. 검사를 먼저 세우니 24건의 실제 불일치가 드러났고, 그것을 해소한 지금은 생성기의 정답(= 현재 파일)이 확정돼 있다. 순서가 반대였다면 생성기가 틀린 상태를 그대로 굳혔을 것이다.

**왜 dark 를 생성하지 않는가.** 다크 값은 Figma 에 없다(2026-09-13 사용자 확정). 원본이 없는 것을 생성할 수는 없다. 다크를 Figma 로 옮기는 결정이 나면 그때 생성 범위를 넓힌다 — §8 의 조건 3 이 그 경우다.
